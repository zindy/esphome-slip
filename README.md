# ESPHome over SLIP: an ESP32 on Home Assistant through a plain USB cable

Connect an ESP32 to a Linux host with nothing but its USB cable. No WiFi, no
Ethernet. The cable provides power **and** a point-to-point IP link (SLIP, Serial
Line IP) over the board's USB-serial bridge, and the normal ESPHome Native API
runs on top of it.

```
 Linux host                                         ESP32 (NodeMCU-style board)
 ┌─────────────────────┐   USB cable (power + serial)   ┌─────────────────────┐
 │ slattach → sl0      │ ═════════════════════════════► │ CP210x/CH340 bridge │
 │ 192.168.254.1       │     SLIP, 115200 baud          │        ↕ UART0      │
 │                     │                                │ lwIP slipif         │
 │ esphome / HA client │ ◄──── ESPHome API, TCP 6053 ─► │ 192.168.254.2       │
 └─────────────────────┘                                └─────────────────────┘
```

On Home Assistant OS there is no `slattach`, so the host side is a small app
(this repository's [`slip_gateway`](slip_gateway)) that does the same job in
userspace:

```
 Home Assistant OS                                  ESP32
 ┌────────────────────────────┐  USB cable          ┌─────────────────────┐
 │ SLIP gateway app           │ ══════════════════► │ CP210x/CH340 bridge │
 │  serial ⇄ TUN "slip0"      │  SLIP, 115200 baud  │        ↕ UART0      │
 │  192.168.254.1             │                     │ lwIP slipif         │
 │ HA Core, ESPHome app, ...  │ ◄─ API, TCP 6053 ─► │ 192.168.254.2       │
 └────────────────────────────┘                     └─────────────────────┘
```

> **Status.** Working end to end on two hosts:
> a Linux PC with `slattach` (ping ~18 ms, API handshake, log streaming), and
> Home Assistant OS 18.4 (Core 2026.10.4) through the
> [SLIP gateway app](#home-assistant-os-the-slip-gateway-app). On Home Assistant
> OS the board is added to the ESPHome integration by IP, its ESP-NOW frames
> reach Home Assistant as events, and **firmware updates over the link work**
> from the ESPHome Device Builder app.
> **Not tested:** boards other than an ESP32 NodeMCU, baud rates other than
> 115200, Home Assistant installs other than Home Assistant OS and a plain Linux
> host. See [Limitations](#limitations).

Tested with: ESP32 NodeMCU (`esp32dev`, original ESP32, 4 MB flash),
ESPHome 2026.10.0 (command line on Linux) and 2026.10.1 (ESPHome Device Builder
app), ESP-IDF 5.5.6, Linux host with the `slip` kernel module and `slattach`
from `net-tools`, Home Assistant OS 18.4.

## Why this is not just a YAML option

ESPHome does not support this out of the box, for three separate reasons, each
of which had to be solved:

1. **Its network layer only knows WiFi, Ethernet, modem and OpenThread.**
   `network::is_connected()` is a header-only inline function that checks those
   and nothing else. The API server calls it every loop and **disconnects every
   client while it returns false**. With a SLIP link the TCP handshake succeeds,
   the client's first packet arrives, and the ESP answers with a TCP reset
   (visible in `tcpdump`). This is the subtle one.
   Fixed by [`patch_network_util.py`](patch_network_util.py).
2. **lwIP's SLIP netif needs glue.** ESP-IDF can compile lwIP's `slipif`
   (`CONFIG_LWIP_SLIP_SUPPORT`) but you must supply the serial I/O hooks
   (`sio_open/sio_send/sio_read/...`). Done in
   [`custom_components/slip`](custom_components/slip).
3. **The USB bridge shares UART0 with the logger.** Anything the firmware logs
   on UART0 corrupts the SLIP stream, so the UART logger is switched off
   (logs still reach you through the API).

## Repository layout

| File | Purpose |
|---|---|
| `my_device.yaml` | Example ESPHome configuration (SLIP link, OTA, ESP-NOW frames forwarded to Home Assistant as events, heartbeat) |
| `custom_components/slip/` | The `slip` component: `__init__.py`, `slip_component.h`, `slip_component.cpp` |
| `patch_network_util.py` | Creates `custom_components/network/` from your installed ESPHome and patches `util.h` |
| `init_slip` | Linux host script: attaches `slattach`, configures `sl0`, checks the ESP answers |
| `slip_ping.py` | Diagnostic tool: speaks SLIP directly to the board, no kernel support needed |
| `slip_gateway/` | Home Assistant OS app: serial ⇄ TUN bridge providing 192.168.254.1 (`config.yaml`, `Dockerfile`, `slipgw.py`) |
| `repository.yaml` | Lets Home Assistant treat this repository as an app repository (see [alternative install](#alternative-add-the-repository-as-an-app-repository)) |

`custom_components/network/` is generated by the patch script. You can commit
it or add it to `.gitignore` and regenerate it.

## Quick start (Linux host)

For Home Assistant OS, do steps 1 to 4 here, then continue with
[Home Assistant OS: the SLIP gateway app](#home-assistant-os-the-slip-gateway-app).

### 1. Requirements

- An ESP32 dev board whose USB-serial bridge is wired to UART0
  (GPIO1 TX / GPIO3 RX). That is the case for most NodeMCU-style boards.
- A Linux host with SLIP support. Check with `sudo modprobe slip`, and install
  `slattach` with `sudo apt install net-tools`.
- ESPHome in a Python virtualenv (the patch script reads the installed copy):

  ```bash
  python3 -m venv esphome-venv
  source esphome-venv/bin/activate
  pip install esphome pyserial
  ```

### 2. Configuration

`my_device.yaml` (the important parts):

```yaml
esphome:
  name: slip-node

esp32:
  board: esp32dev
  framework:
    type: esp-idf                      # required: the slip component uses ESP-IDF's lwIP
    sdkconfig_options:
      CONFIG_LWIP_SLIP_SUPPORT: "y"

external_components:
  - source:
      type: local
      path: custom_components
    components: [slip, network]        # `network` = the patched local copy

network:                               # api requires it even without wifi/ethernet

logger:
  baud_rate: 0                         # UART0 belongs to SLIP; logs still go to the API

uart:
  id: slip_uart
  tx_pin: GPIO1                        # UART0 = the USB bridge
  rx_pin: GPIO3
  baud_rate: 115200
  rx_buffer_size: 1024

slip:
  uart_id: slip_uart
  local_ip: 192.168.254.2              # the ESP
  gateway: 192.168.254.1               # the host
  subnet: 255.255.255.0
  diagnostics: false

api:
  reboot_timeout: 0s                   # don't reboot when no client is connected

ota:                                   # needed for updates over the link
  - platform: esphome
```

### 3. Patch ESPHome's network component

From the project folder, with the virtualenv active:

```bash
python3 patch_network_util.py            # creates custom_components/network/
python3 patch_network_util.py --check    # report state (exit 0 = patched and up to date)
```

The script copies the `network` component from the ESPHome you have installed
and adds ~10 lines to its `util.h`. It is idempotent, and records which ESPHome
version it was made for. After upgrading ESPHome, run it again with `--force`.
(A copy generated from ESPHome 2026.10.0 also compiled in the 2026.10.1 Device
Builder app. Regenerate it anyway after upgrades.)

### 4. Build and flash

Over the same USB cable, once, the normal way:

```bash
esphome run my_device.yaml --device /dev/ttyUSB0
```

There is no output after the upload, because the UART logger is off. That is expected.

### 5. Bring up the link on the host

Find the board's serial port. Use the stable `by-path` name: `/dev/ttyUSBn`
numbers change between reboots and re-plugs, and attaching SLIP to the wrong
port (a Zigbee or Z-Wave stick, say) breaks whatever uses it. For that reason
`init_slip` insists on an explicit device and refuses to guess.

```bash
ls -l /dev/serial/by-path/
sudo ./init_slip /dev/serial/by-path/pci-0000:00:1a.7-usb-0:1.4:1.0-port0
```

Which does, in essence:

```bash
slattach -L -p slip -s 115200 "$DEV" &     # detached, so it survives logging out
ip addr add 192.168.254.1 peer 192.168.254.2 dev sl0
ip link set sl0 mtu 1500 up
sleep 5                                    # opening the port resets the board
ping -c 2 192.168.254.2
```

It refuses to start if another `slattach` is running or the port is busy.
Stop the link with `sudo pkill slattach` (and do so before flashing over USB).

### 6. Test

```bash
ping 192.168.254.2
nc -zv 192.168.254.2 6053                           # API port
esphome logs my_device.yaml --device 192.168.254.2
```

A successful run shows `Successful handshake with slip-node` and the device log.
If you added a heartbeat to the YAML (see below) you will see it every 5 s.

```yaml
interval:
  - interval: 5s
    then:
      - logger.log: "hello over SLIP"
```

## Home Assistant OS: the SLIP gateway app

Home Assistant OS has a minimal userland: no `slattach`, and I did not check
whether its kernel ships the `slip` module. Instead of fighting that, the
[`slip_gateway`](slip_gateway) app does the host side in userspace:
`slipgw.py` opens the board's serial port, creates a TUN interface (`slip0`)
with `192.168.254.1 peer 192.168.254.2`, and moves IPv4 packets between the two
using SLIP framing (RFC 1055). The app runs with host networking and the
`NET_ADMIN` privilege, so `slip0` appears on the host. Home Assistant Core uses
host networking too, so it reaches the board at 192.168.254.2. Other apps (the
Terminal & SSH app, the ESPHome Device Builder app) reach it through the host's
routing.

(Home Assistant 2026.2 renamed "add-ons" to "apps". Same thing, new name: look
under Settings → Apps.)

### Install as a local app

1. Install and start the **Samba share** app (Settings → Apps → app store) and
   set its credentials.
2. From your computer, open the share named `addons` (`\\homeassistant\addons`
   on Windows, `smb://homeassistant.local/addons` on macOS and Linux; the
   share name and host name may differ on your system). Copy the whole
   `slip_gateway` folder from this repository into it, so that you end up with
   `addons/slip_gateway/config.yaml`, `Dockerfile` and `slipgw.py`.
3. In Settings → Apps → app store, open the ⋮ menu and choose *Check for
   updates*. "SLIP gateway" shows up under local apps. Install it. The image is
   built on the machine itself, which takes a minute or two and needs internet
   access.
4. Plug in the ESP32 (flashed as described above). In the app's Configuration
   tab set `device` to the board's serial port (Settings → System → Hardware
   lists the serial devices; the default is `/dev/ttyUSB0`). Prefer a stable
   `/dev/serial/by-id/...` path if the app can see one, because `ttyUSBn`
   numbers change when devices are re-plugged.
5. Start the app. Enable *Start on boot* and *Watchdog*.
6. Check the app's Log tab: you should see `slip0 up: 192.168.254.1 <->
   192.168.254.2` and `serial open: ...`. From the Terminal & SSH app,
   `ping 192.168.254.2` should answer (about 25 ms for a small packet).

After changing `slipgw.py` or the `Dockerfile`, copy the file over and use the
app's *Rebuild* button. Changes to the *option list* in `config.yaml` are not
picked up by an already installed app (a new option I added simply vanished
when I saved it in the app's YAML editor); bump `version`, reload the app store
and update, or give the option a default inside `slipgw.py`.

### Alternative: add the repository as an app repository

Settings → Apps → app store → ⋮ → Repositories, and add this repository's
GitHub URL. `repository.yaml` at the repository root and the
`slip_gateway/config.yaml` folder are what Home Assistant looks for. The app is
then built on the machine like a local one. **I have not tested this route**;
the local install above is the one that was used.

### Options

| Option | Default | Meaning |
|---|---|---|
| `device` | `/dev/ttyUSB0` | Serial port of the ESP32's USB bridge |
| `baud` | `115200` | Must match `uart: baud_rate` in the firmware |
| `ifname` | `slip0` | Name of the TUN interface |
| `local_ip` | `192.168.254.1` | The host end (must match `slip: gateway`) |
| `peer_ip` | `192.168.254.2` | The ESP end (must match `slip: local_ip`) |
| `mtu` | `1500` | Interface MTU |
| `trace_port` | `0` | If non-zero, log one line per TCP packet to or from that port (for debugging; `3232` is the OTA port) |

### What the app logs

Every 10 s, if anything changed, a `stats:` line:

```
stats: to_esp_pkts=162 to_esp_bytes=9991 to_esp_max=332 from_esp_pkts=112 from_esp_bytes=9794 from_esp_max=434 discarded_frames=1 discarded_bytes=1591
```

`discarded_*` counts frames from the board that were not valid IPv4 packets.
One discarded frame of about 1.6 KB right after start is normal: opening the
serial port resets the board, and its ROM bootloader prints at 74880 baud.
Anything that keeps growing is worth a look.

### Notes

- The app owns the serial port while it runs. **Stop it before flashing over
  USB**, then start it again.
- Opening the serial port resets the board, so restarting the app reboots the
  ESP32. The script keeps DTR and RTS low when opening the port to make that
  less likely; I did not check whether that fully prevents the reset on every
  board.
- The app has been tested on one Home Assistant OS machine. `config.yaml`
  declares `amd64`, `aarch64` and `armv7`, but I have only run it on one of them.
- Name resolution does not work across the link: `ping slip-node` fails on the
  Home Assistant host, and Home Assistant's ESPHome integration has to be given
  the IP address.

## Using the board from Home Assistant

Add the device by IP address (Settings → Devices & services → ESPHome →
192.168.254.2). mDNS discovery does not cross a point-to-point link.

### Forwarding raw ESP-NOW frames as events

The example `my_device.yaml` listens for ESP-NOW broadcasts and does **no
interpretation on the ESP32**. Every frame is forwarded to Home Assistant as an
event, and the logic lives in Home Assistant automations, so the firmware only
has to be flashed once:

```yaml
espnow:
  channel: 1
  auto_add_peer: true
  on_broadcast:
    then:
      - homeassistant.event:
          event: esphome.espnow_broadcast
          data_template:
            mac: "{{ mac }}"
            rssi: "{{ rssi }}"
            len: "{{ len }}"
            cmd: "{{ cmd }}"
            payload: "{{ payload }}"
          variables:
            mac: !lambda |-
              char b[18];
              snprintf(b, sizeof(b), "%02X:%02X:%02X:%02X:%02X:%02X",
                       info.src_addr[0], info.src_addr[1], info.src_addr[2],
                       info.src_addr[3], info.src_addr[4], info.src_addr[5]);
              return std::string(b);
            rssi: !lambda |-
              return (int) info.rx_ctrl->rssi;
            len: !lambda |-
              return (int) size;
            cmd: !lambda |-
              return size > 0 ? (int) data[0] : -1;
            payload: !lambda |-
              static const char *H = "0123456789ABCDEF";
              std::string s;
              for (size_t i = 0; i < size && i < 250; i++) {
                s += H[data[i] >> 4];
                s += H[data[i] & 15];
              }
              return s;
```

For the device to be allowed to fire events, tick **"Allow the device to
perform Home Assistant actions"** in the ESPHome integration's options for that
device. Without it Home Assistant drops them silently.

Each event is `esphome.espnow_broadcast` with `mac`, `rssi`, `len`, `cmd` (the
first payload byte, or -1) and `payload` (hex string, up to 250 bytes). You can
watch them under Settings → Tools → Events (Developer tools → Events in older
versions): enter the event name in the listen box and press the doorbell. A first automation:

```yaml
alias: ESP-NOW dispatcher
mode: single
max_exceeded: silent
triggers:
  - trigger: event
    event_type: esphome.espnow_broadcast
actions:
  - choose:
      - conditions:
          - condition: template
            value_template: >
              {{ trigger.event.data.mac == 'AA:BB:CC:DD:EE:FF'
                 and trigger.event.data.cmd | int(-1) == 2 }}
        sequence:
          - action: notify.notify
            data:
              message: "Doorbell"
          - delay: "00:00:02"     # swallow the sender's repeated frames
```

`mode: single` plus the trailing `delay` turns a burst of repeated frames into
one reaction. Replace the MAC address with your sender's.

### Heartbeat

`hello over SLIP` in the YAML is only a log line. For something Home Assistant
can watch, the example configuration also publishes a `Heartbeat` counter sensor
every 5 s, next to the `Status` binary sensor (on while the API connection is up)
and `Uptime`. A watchdog automation:

```yaml
alias: SLIP node silent
triggers:
  - trigger: state
    entity_id: sensor.slip_node_heartbeat
    for: "00:00:30"
actions:
  - action: persistent_notification.create
    data:
      message: "slip-node heartbeat stopped"
```

It fires when the counter has not changed for 30 s (adjust the entity ID).

## OTA updates over the link

Firmware updates work over the SLIP link, from the ESPHome Device Builder app.

1. Put `ota: - platform: esphome` in the YAML. **The first flash that adds it
   has to go over USB** (stop the gateway app, flash, restart the gateway app).
   Without it there is nothing listening on port 3232.
2. Copy `my_device.yaml` and `custom_components/` (including the generated
   `network` copy) into the folder where the Device Builder app keeps its YAML
   files. You can reach it through the Samba share; which share and path depends
   on your version of the app.
3. Build as usual. The first build downloads the ESP-IDF toolchain and takes a
   while.
4. In the install dialog choose the option to install to a host and type
   `192.168.254.2`. **Do not use the default `slip-node.local`**: it does not
   resolve.
5. Keep the gateway app running. The link is serial-limited, so the upload
   is slow: in one run the 742 KB image (514 KB compressed) took 82 s to upload,
   and the whole update 83 s. The heartbeat and events pause while the upload is
   being received.

The Device Builder dashboard will show the device as **offline** and say that
the configuration has "no network component". That is cosmetic. The dashboard
decides whether a device is online by resolving and pinging its name, and the
only addresses it knows about come from WiFi, Ethernet and OpenThread. Installing
to the IP address bypasses all of it, and a device that says "offline" updated
fine.

From a Linux host with the link up, `esphome run my_device.yaml --device
192.168.254.2` should do the same job. I did not test that exact form (the
update was done from the Device Builder app).

## How the firmware works

- `slip_component.cpp` registers a lwIP netif with `slipif_init`, input function
  `tcpip_input` and the default route, under `LOCK_TCPIP_CORE()`.
- **Receive path.** ESP-IDF's lwIP is built here with `SLIP_USE_RX_THREAD=0`
  (the component prints which mode it was built with in its config dump), so
  lwIP has no SLIP receive thread of its own: someone has to call
  `slipif_poll()`. The component creates a FreeRTOS task, `rx_task_`, that moves
  bytes from ESPHome's UART buffer into a 1024-byte queue and then calls
  `slipif_poll()`, which reads that queue through `sio_tryread()` and hands
  complete packets to lwIP via `tcpip_input`.
- **Why a task and not `loop()`.** An OTA upload is received inside ESPHome's
  main loop, which stays blocked for as long as the transfer is waiting for
  data. With the receive path in `loop()`, the bytes the upload was waiting for
  sat in the queue until the queue overflowed and the handler timed out (see the
  table below). `rx_task_` keeps running while the main loop is blocked.
- Transmit is `sio_send()` → `UARTDevice::write_byte()`, called from lwIP's
  own thread.
- Every `loop()` the component publishes the netif state to
  `network::custom_interface_connected()`, which the patched
  `network::is_connected()` honours. Without that flag the API server kills every
  connection.
- If the main loop stalls and the receive path notices (a gap, a queue that
  filled up, dropped bytes), `loop()` logs a one-line warning once it runs
  again: `rx_task max gap ... queue high-water ... queue drops ...`. It is silent
  when everything is normal.

## Things that went wrong (and what each one looked like)

If you hit one of these, you now know the cause.

| Symptom | Cause | Fix |
|---|---|---|
| `Component not found: slip` | `custom_components/` is no longer auto-loaded | `external_components` with a `local` source (see the YAML) |
| `Component api requires component network` | No WiFi/Ethernet configured | Add a bare `network:` |
| `AttributeError: ... has no attribute 'ipv4'` | `cv.ipv4` does not exist | `cv.ipv4address` |
| `ipaddr_aton` type error / odd behaviour | lwIP built with IPv6 expects `ip_addr_t*` | `ip4addr_aton` |
| Random crashes or stalls | Input function was `ip_input`, called from the SLIP thread outside lwIP's tcpip thread | Use `tcpip_input` and `LOCK_TCPIP_CORE()` |
| `ifconfig: sl0: No such device` right after `slattach &` | `ifconfig` ran before the kernel created `sl0` | Wait for `sl0` (`init_slip` does) |
| `sl0` vanishes when you close your ssh session | `slattach` was a child of the shell and got a hangup | `init_slip` starts it detached (`setsid`) |
| `init_slip` says the device is in use, or another `slattach` is running | Something already holds the port or an earlier link is still up | `sudo pkill slattach`, check `fuser -v <device>` |
| `usb usbN-portM: disabled by hub (EMI?)` in `dmesg` right after `slattach` starts, and the adapter(s) vanish | Seen on one host, behind a small hub: the port was disabled as soon as the board was reset by opening the serial port. Cause not confirmed (power is my guess). The same messages (`... disabled by hub (EMI?), re-enabling...`, `unable to enumerate USB device`) were also reported on the Home Assistant OS machine | Try a port directly on the machine or a powered hub, and a different cable; unplug and re-plug the board |
| `ping` fails; `ip -s link show sl0` shows TX packets, RX 0 | Opening the serial port resets the board (DTR/RTS) and the pings went out while it rebooted | Wait ~5 s after `slattach` (or after starting the app) before pinging |
| `ping` works, but the API client gets `Connection reset by peer` and reconnects forever; `tcpdump` shows `[R.]` right after the client's first data packet | `network::is_connected()` is false, so the API server disconnects clients | `patch_network_util.py` |
| Device logs nothing | Nothing logs when idle. UART logging is off, but API log streaming still works | Add the heartbeat `interval:` to verify |
| Flashing fails with `/dev/ttyUSB0` busy | `slattach` (or the gateway app) holds the port | `sudo pkill slattach` or stop the app, flash, restart the link |
| Boot-time garbage on the serial port | ROM bootloader messages are printed at 74880 baud | Harmless; SLIP drops non-packet bytes (the gateway app counts them in `discarded_frames`) |
| No "Add-ons" in Settings (Home Assistant 2026.2 and later) | Renamed | Look under Settings → Apps |
| `ping slip-node` or `slip-node.local` fails on the Home Assistant host | mDNS does not cross the link and nothing registers the name | Use the IP address |
| ESP-NOW frames reach the log but no event shows up in Home Assistant | The device is not allowed to perform Home Assistant actions | Tick "Allow the device to perform Home Assistant actions" in the ESPHome integration options |
| OTA from the dashboard never starts; the card says offline and `slip-node.local` does not resolve | The dashboard finds devices through mDNS/ping of the name | In the install dialog type the IP address as host |
| OTA connects, handshake completes, then `ERROR receiving update prepare result: Unknown error from ESP`; the device log shows `Read OTA type failed` after about 106 s | The receive path ran in `loop()`, which is blocked while the OTA handler waits for data: incoming bytes filled the queue, the next bytes never reached the handler, and it timed out. `rx_task max gap` stayed tiny while `queue drops` grew by thousands, `consumed` stayed far below `uart_rx`, and pings sent during the stall were answered only afterwards | Run `slipif_poll()` from `rx_task_` instead of `loop()` (done in this repository) |
| `WARNING [api] The 'variables' value ... is missing the !lambda tag` when compiling | ESPHome now wants the `!lambda` tag on lambdas under `homeassistant.event` `variables`; untagged ones are compiled as lambdas for now but will be sent as literal text from ESPHome 2027.3.0 | Write `mac: !lambda \|-` (etc.), as in `my_device.yaml` |
| An option added to the gateway app's `config.yaml` vanishes when saved in the app's YAML editor | The installed app keeps its old option list | Bump `version` and update the app, or put the default in `slipgw.py` and rebuild |

### A trick for telling firmware builds apart

With the link idle, the RX packet count in `ip -s link show sl0` stays constant on a
build with `diagnostics: false`, and should increase about every 2 s on a build
with diagnostics on (the status text arrives as non-IP frames). Don't rely on
`RX errors` for this: it stayed at 0 in testing.

## Diagnostics

Set `diagnostics: true` under `slip:` and the firmware writes a status line
every 2 s on the serial port, wrapped in SLIP END bytes:

```
SLIPDIAG up=1 link=1 default=1 ip=192.168.254.2 uart_rx=44 consumed=44 sent=44 opened=1 drops=0
```

| Field | Meaning |
|---|---|
| `up`, `link`, `default` | netif state (all should be 1) |
| `opened` | times lwIP opened the serial device (≥ 1) |
| `uart_rx` | bytes received from the UART |
| `consumed` | bytes read by lwIP (should follow `uart_rx`) |
| `sent` | bytes written by lwIP |
| `drops` | bytes lost because the RX queue was full |

`slip_ping.py` talks SLIP directly to the board and needs neither `slattach` nor
the kernel driver. Stop `slattach` first:

```bash
python3 slip_ping.py /dev/ttyUSB0
```

It waits for the board to boot, sends 5 ICMP echo requests and prints every
frame that comes back, including the `SLIPDIAG` lines. **Do not leave diagnostics
on for normal use:** the status text is injected into the same byte stream as the
IP traffic and can corrupt packets.

Other useful tools:

```bash
sudo tcpdump -i sl0 -nn -X tcp port 6053   # see who sends the RST/FIN
sudo picocom -b 115200 /dev/ttyUSB0        # watch the boot log (stop slattach first)
```

On Home Assistant OS, set the gateway app's `trace_port` option to log one line
per TCP packet (direction, flags, sequence and acknowledgement numbers, payload
length, window) for a given port, and watch the `stats:` lines for discarded
frames. Pinging with larger payloads (`ping -s 1400 192.168.254.2`) is a quick
check that full-size packets survive the link: replies take longer in step
with the size, about 270 ms for a 1400-byte payload at 115200 baud.

## Limitations

- **Home Assistant OS is tested on one machine**, through the gateway app
  (Home Assistant OS 18.4). Other installation types (Supervised, Container,
  Core) were not tried; on a plain Linux host the `slattach` route from the
  quick start applies.
- **Flashing over USB needs the port.** Stop `slattach` or the gateway app
  before every USB upload. OTA over the link works, but only by typing the IP
  address as the host, and the dashboard will show the device as offline.
- **Throughput is serial-limited.** 115200 baud is at most ~11 KB/s, and the
  measured round-trip time is ~18 ms for a ping on a Linux host and about 25 ms
  through the app. Plenty for sensors, not for bulk data. An OTA upload of the
  example firmware (514 KB compressed) took about 80 s. Higher baud rates are
  untested.
- **One device per serial port**, and the host owns the port while the link is up.
- **Version coupling.** The `network` override copies an ESPHome component. It
  is regenerated from your installed version by the script, but the patch
  anchors on the exact source text and will refuse to apply if upstream changes
  `util.h` (it fails loudly rather than guessing).
- **Boards**: the YAML assumes the USB bridge is on UART0 (GPIO1/3). Boards with
  native USB (ESP32-S2/S3/C3) are different hardware paths and untested here.
- ESP-IDF framework only; no Arduino.
- IPv4 only.
- The receive-path fix assumes ESP-IDF's lwIP is built without a SLIP receive
  thread (`SLIP_USE_RX_THREAD=0`), as it is with ESP-IDF 5.5.6. The component
  prints which mode it was built with. A different ESP-IDF configuration may
  need a different arrangement.

## Suggested upstream change

The root problem is that ESPHome has no way to register a custom network
interface: `is_connected()` is hard-wired to its four known components. A small
hook (a registry of "extra interface is connected" callbacks, or a generic
`network` interface component) would let this work without overriding a core
component. If you pick this up upstream, I would be glad to hear about it.

A second, smaller point: the Device Builder dashboard can only learn a device's
address from the WiFi, Ethernet or OpenThread configuration, so a device on a
custom interface always looks offline. An address hook there would remove the
need to type the IP into the install dialog.
