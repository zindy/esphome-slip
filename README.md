# ESPHome over SLIP: an ESP32 on Home Assistant through a plain USB cable

Connect an ESP32 to a Linux host with nothing but its USB cable. No WiFi, no
Ethernet. The cable provides power **and** a point-to-point IP link (SLIP, Serial
Line IP) over the board's USB-serial bridge, and the normal ESPHome Native API
runs on top of it.

```
 Linux host                                         ESP32 (NodeMCU-style board)
 ┌─────────────────────┐   USB cable (power + serial)   ┌─────────────────────┐
 │ slattach → sl0      │ ═════════════════════════════► │ CP210x/CH340 bridge │
 │ 192.168.254.1       │     SLIP, 115200 baud          │        ↕ UART0      │
 │                     │                                │ lwIP slipif         │
 │ esphome / HA client │ ◄──── ESPHome API, TCP 6053 ─► │ 192.168.254.2       │
 └─────────────────────┘                                └─────────────────────┘
```

> **Status.** Working end to end on a Linux PC: ping (~18 ms), API handshake,
> log streaming. **Not tested:** Home Assistant OS, OTA updates over the link,
> boards other than an ESP32 NodeMCU, baud rates other than 115200. See
> [Limitations](#limitations).

Tested with: ESP32 NodeMCU (`esp32dev`, original ESP32, 4 MB flash),
ESPHome 2026.10.0, ESP-IDF 5.5.6, Linux host with the `slip` kernel module and
`slattach` from `net-tools`.

## Why this is not just a YAML option

ESPHome does not support this out of the box, for three separate reasons, each
of which had to be solved:

1. **Its network layer only knows WiFi, Ethernet, modem and OpenThread.**
   `network::is_connected()` is a header-only inline function that checks those
   and nothing else. The API server calls it every loop and **disconnects every
   client while it returns false**. With a SLIP link the TCP handshake succeeds,
   the client's first packet arrives, and the ESP answers with a TCP reset
   (visible in `tcpdump`). This is the subtle one.
   Fixed by [`patch_network_util.py`](patch_network_util.py).
2. **lwIP's SLIP netif needs glue.** ESP-IDF can compile lwIP's `slipif`
   (`CONFIG_LWIP_SLIP_SUPPORT`) but you must supply the serial I/O hooks
   (`sio_open/sio_send/sio_read/...`). Done in
   [`custom_components/slip`](custom_components/slip).
3. **The USB bridge shares UART0 with the logger.** Anything the firmware logs
   on UART0 corrupts the SLIP stream, so the UART logger is switched off
   (logs still reach you through the API).

## Repository layout

| File | Purpose |
|---|---|
| `my_device.yaml` | Example ESPHome configuration |
| `custom_components/slip/` | The `slip` component: `__init__.py`, `slip_component.h`, `slip_component.cpp` |
| `patch_network_util.py` | Creates `custom_components/network/` from your installed ESPHome and patches `util.h` |
| `init_slip` | Host script: attaches `slattach`, configures `sl0`, checks the ESP answers |
| `slip_ping.py` | Diagnostic tool: speaks SLIP directly to the board, no kernel support needed |

`custom_components/network/` is generated by the patch script. You can commit
it or add it to `.gitignore` and regenerate it.

## Quick start

### 1. Requirements

- An ESP32 dev board whose USB-serial bridge is wired to UART0
  (GPIO1 TX / GPIO3 RX). That is the case for most NodeMCU-style boards.
- A Linux host with SLIP support. Check with `sudo modprobe slip`, and install
  `slattach` with `sudo apt install net-tools`.
- ESPHome in a Python virtualenv (the patch script reads the installed copy):

  ```bash
  python3 -m venv esphome-venv
  source esphome-venv/bin/activate
  pip install esphome pyserial
  ```

### 2. Configuration

`my_device.yaml` (the important parts):

```yaml
esphome:
  name: slip-node

esp32:
  board: esp32dev
  framework:
    type: esp-idf                      # required: the slip component uses ESP-IDF's lwIP
    sdkconfig_options:
      CONFIG_LWIP_SLIP_SUPPORT: "y"

external_components:
  - source:
      type: local
      path: custom_components
    components: [slip, network]        # `network` = the patched local copy

network:                               # api requires it even without wifi/ethernet

logger:
  baud_rate: 0                         # UART0 belongs to SLIP; logs still go to the API

uart:
  id: slip_uart
  tx_pin: GPIO1                        # UART0 = the USB bridge
  rx_pin: GPIO3
  baud_rate: 115200
  rx_buffer_size: 1024

slip:
  uart_id: slip_uart
  local_ip: 192.168.254.2              # the ESP
  gateway: 192.168.254.1               # the host
  subnet: 255.255.255.0
  diagnostics: false

api:
  reboot_timeout: 0s                   # don't reboot when no client is connected
```

### 3. Patch ESPHome's network component

From the project folder, with the virtualenv active:

```bash
python3 patch_network_util.py            # creates custom_components/network/
python3 patch_network_util.py --check    # report state (exit 0 = patched and up to date)
```

The script copies the `network` component from the ESPHome you have installed
and adds ~10 lines to its `util.h`. It is idempotent, and records which ESPHome
version it was made for. After upgrading ESPHome, run it again with `--force`.

### 4. Build and flash

Over the same USB cable, once, the normal way:

```bash
esphome run my_device.yaml --device /dev/ttyUSB0
```

There is no output after the upload, because the UART logger is off. That is expected.

### 5. Bring up the link on the host

Find the board's serial port. Use the stable `by-path` name: `/dev/ttyUSBn`
numbers change between reboots and re-plugs, and attaching SLIP to the wrong
port (a Zigbee or Z-Wave stick, say) breaks whatever uses it. For that reason
`init_slip` insists on an explicit device and refuses to guess.

```bash
ls -l /dev/serial/by-path/
sudo ./init_slip /dev/serial/by-path/pci-0000:00:1a.7-usb-0:1.4:1.0-port0
```

Which does, in essence:

```bash
slattach -L -p slip -s 115200 "$DEV" &     # detached, so it survives logging out
ip addr add 192.168.254.1 peer 192.168.254.2 dev sl0
ip link set sl0 mtu 1500 up
sleep 5                                    # opening the port resets the board
ping -c 2 192.168.254.2
```

It refuses to start if another `slattach` is running or the port is busy.
Stop the link with `sudo pkill slattach` (and do so before flashing).

### 6. Test

```bash
ping 192.168.254.2
nc -zv 192.168.254.2 6053                           # API port
esphome logs my_device.yaml --device 192.168.254.2
```

A successful run shows `Successful handshake with slip-node` and the device log.
If you added a heartbeat to the YAML (see below) you will see it every 5 s.

```yaml
interval:
  - interval: 5s
    then:
      - logger.log: "hello over SLIP"
```

### 7. Home Assistant

Add the device by IP address (Settings → Devices & services → ESPHome →
192.168.254.2). mDNS discovery does not cross a point-to-point link. The host
running Home Assistant needs the SLIP link from step 5 itself, which is the
untested part (see [Limitations](#limitations)).

## How the firmware works

- `slip_component.cpp` registers a lwIP netif with `slipif_init`, input function
  `tcpip_input` and the default route, under `LOCK_TCPIP_CORE()`.
- lwIP's SLIP receive thread calls `sio_read()`, which blocks on a FreeRTOS queue.
  `loop()` drains ESPHome's UART buffer into that queue (with a high-frequency
  loop request, so it is drained fast).
- Transmit is `sio_send()` → `UARTDevice::write_byte()`.
- Every `loop()` the component publishes the netif state to
  `network::custom_interface_connected()`, which the patched
  `network::is_connected()` honours. Without that flag the API server kills every
  connection.

## Things that went wrong (and what each one looked like)

If you hit one of these, you now know the cause.

| Symptom | Cause | Fix |
|---|---|---|
| `Component not found: slip` | `custom_components/` is no longer auto-loaded | `external_components` with a `local` source (see the YAML) |
| `Component api requires component network` | No WiFi/Ethernet configured | Add a bare `network:` |
| `AttributeError: ... has no attribute 'ipv4'` | `cv.ipv4` does not exist | `cv.ipv4address` |
| `ipaddr_aton` type error / odd behaviour | lwIP built with IPv6 expects `ip_addr_t*` | `ip4addr_aton` |
| Random crashes or stalls | Input function was `ip_input`, called from the SLIP thread outside lwIP's tcpip thread | Use `tcpip_input` and `LOCK_TCPIP_CORE()` |
| `ifconfig: sl0: No such device` right after `slattach &` | `ifconfig` ran before the kernel created `sl0` | Wait for `sl0` (`init_slip` does) |
| `sl0` vanishes when you close your ssh session | `slattach` was a child of the shell and got a hangup | `init_slip` starts it detached (`setsid`) |
| `init_slip` says the device is in use, or another `slattach` is running | Something already holds the port or an earlier link is still up | `sudo pkill slattach`, check `fuser -v <device>` |
| `usb usbN-portM: disabled by hub (EMI?)` in `dmesg` right after `slattach` starts, and the adapter(s) vanish | Seen on one host, behind a small hub: the port was disabled as soon as the board was reset by opening the serial port. Cause not confirmed (power is my guess) | Try a port directly on the machine or a powered hub, and a different cable |
| `ping` fails; `ip -s link show sl0` shows TX packets, RX 0 | Opening the serial port resets the board (DTR/RTS) and the pings went out while it rebooted | Wait ~5 s after `slattach` before pinging |
| `ping` works, but the API client gets `Connection reset by peer` and reconnects forever; `tcpdump` shows `[R.]` right after the client's first data packet | `network::is_connected()` is false, so the API server disconnects clients | `patch_network_util.py` |
| Device logs nothing | Nothing logs when idle. UART logging is off, but API log streaming still works | Add the heartbeat `interval:` to verify |
| Flashing fails with `/dev/ttyUSB0` busy | `slattach` holds the port | `sudo pkill slattach`, flash, restart the link |
| Boot-time garbage on the serial port | ROM bootloader messages are printed at 74880 baud | Harmless; SLIP drops non-packet bytes |

### A trick for telling firmware builds apart

With the link idle, the RX packet count in `ip -s link show sl0` stays constant on a
build with `diagnostics: false`, and should increase about every 2 s on a build
with diagnostics on (the status text arrives as non-IP frames). Don't rely on
`RX errors` for this: it stayed at 0 in testing.

## Diagnostics

Set `diagnostics: true` under `slip:` and the firmware writes a status line
every 2 s on the serial port, wrapped in SLIP END bytes:

```
SLIPDIAG up=1 link=1 default=1 ip=192.168.254.2 uart_rx=44 consumed=44 sent=44 opened=1 drops=0
```

| Field | Meaning |
|---|---|
| `up`, `link`, `default` | netif state (all should be 1) |
| `opened` | times lwIP's SLIP thread opened the serial device (≥ 1) |
| `uart_rx` | bytes received from the UART |
| `consumed` | bytes read by lwIP's SLIP thread (should follow `uart_rx`) |
| `sent` | bytes written by lwIP |
| `drops` | bytes lost because the RX queue was full |

`slip_ping.py` talks SLIP directly to the board and needs neither `slattach` nor
the kernel driver. Stop `slattach` first:

```bash
python3 slip_ping.py /dev/ttyUSB0
```

It waits for the board to boot, sends 5 ICMP echo requests and prints every
frame that comes back, including the `SLIPDIAG` lines. **Do not leave diagnostics
on for normal use:** the status text is injected into the same byte stream as the
IP traffic and can corrupt packets.

Other useful tools:

```bash
sudo tcpdump -i sl0 -nn -X tcp port 6053   # see who sends the RST/FIN
sudo picocom -b 115200 /dev/ttyUSB0        # watch the boot log (stop slattach first)
```

## Limitations

- **Home Assistant OS is untested.** Home Assistant OS has a minimal userland and may
  not ship `slattach` or the `slip` kernel module (`sudo modprobe slip` is the
  first thing to check). Alternatives: a Home Assistant install on a regular
  Linux distribution, a PPP link instead of SLIP, or a small host-side bridge
  process.
- **Flashing needs the port.** Stop `slattach` before every upload. OTA over
  the link is untested.
- **Throughput is serial-limited.** 115200 baud is at most ~11 KB/s, and the
  measured round-trip time is ~18 ms. Plenty for sensors, not for bulk data.
  Higher baud rates are untested.
- **One device per serial port**, and the host owns the port while the link is up.
- **Version coupling.** The `network` override copies an ESPHome component. It
  is regenerated from your installed version by the script, but the patch
  anchors on the exact source text and will refuse to apply if upstream changes
  `util.h` (it fails loudly rather than guessing).
- **Boards**: the YAML assumes the USB bridge is on UART0 (GPIO1/3). Boards with
  native USB (ESP32-S2/S3/C3) are different hardware paths and untested here.
- ESP-IDF framework only; no Arduino.
- IPv4 only.

## Suggested upstream change

The root problem is that ESPHome has no way to register a custom network
interface: `is_connected()` is hard-wired to its four known components. A small
hook (a registry of "extra interface is connected" callbacks, or a generic
`network` interface component) would let this work without overriding a core
component. If you pick this up upstream, I would be glad to hear about it.
